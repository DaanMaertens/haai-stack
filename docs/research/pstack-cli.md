# How pstack integrates CLIs into its skill stack

Research for [issue #3](https://github.com/DaanMaertens/haai-stack/issues/3). Terms follow `GLOSSARY.md`: Harness, Agent host, Skill stack, Tool CLI, Orchestrator CLI.

## TL;DR

1. pstack ships **Tool CLIs only, and no Orchestrator CLI**. It has four Bun/TypeScript, Node and bash programs bundled inside the `poteto-mode` skill folder: `orch`, `watch-pr`, `check-plan.mjs` and `worktree-audit.sh`. A fifth, `log.sh`, sits in `show-me-your-work`. `orch` describes itself as "plain-file orchestrate bookkeeping" and "never spawns, waits, or wakes anything".
2. The direction is always **skill → CLI**. Playbook prose tells the agent to shell out (`bun scripts/orch/orch.ts …`, `scripts/watch-pr/watch-pr`). No CLI invokes a skill or an agent.
3. Orchestration is **agentic, inside the Agent host**. A coordinator chat spawns subagents through the host's Task tool, Cursor cloud agents run AFK, and Cursor's built-in `/loop` provides wakes. The CLIs only keep state and answer status queries.
4. State lives in **plain files**: `units.tsv`, `ledger.tsv`, `inbox/`, `gates.md`, `frontier.json`, `preferences.md`, a derived `status.md` and a `decisions.tsv` trail. These sit in a per-project folder in the "agent's store", with a pid lock.
5. Supported Agent hosts are **Cursor (native) and Claude Code**, the latter through a generated plugin tree plus a name-mapping adapter doc. Distribution is the `cursor/plugins` marketplace. Ports to Codex, Pi, OpenCode and T3 are community forks, not upstream.

**There is no Orchestrator CLI.** The orchestrate playbook is explicit: "The loop is agentic end to end. Agents are spawned, resumed, and drained only through the Task tool. … State reads and writes go through `scripts/orch/orch.ts` at drain points, one command in and one line out. The CLI never spawns, waits, or wakes anything." ([orchestrate.md L15](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/orchestrate.md#L15)). pstack does not drive a headless Agent host session from outside.

Some things the skills reference are not shipped in pstack: `control-cli`/`control-ui` and `/deslop` (in `cursor-team-kit`), and `/loop`/`/autopilot` (Cursor built-ins) ([README L255-L263](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/README.md#L255-L263)). I did not read `control-cli`, so whether it is a Tool CLI or a skill wrapper around one is unverified here.

## How skills and CLIs connect

- **Skill → CLI, by prose instruction.** A playbook step names the command and its flags, and the agent runs it with its shell tool. For example, orchestrate says "Begin each batch with `orch inbox drain`" and "writes the resulting rows through `orch unit add`, `orch unit set`, and `orch ledger record`, runs `orch status`" ([orchestrate.md L71-L76](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/orchestrate.md#L71-L76)). Babysit says "status comes from `scripts/watch-pr/watch-pr`. Run it directly." ([babysit.md L12](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/babysit.md#L12)).
- **Output shaped for the agent's context window.** `orch` prints compact rows capped at `DISPLAY_LIMIT = 4`, with "... N more; use --json" ([orch.ts L30, L147-L162](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/orch/orch.ts#L147-L162)). `orch status` prints three lines: counts, what changed, and open gates ([orch.ts L177-L190](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/orch/orch.ts#L177-L190)). A drain turn ends with those three lines ([orchestrate.md L76](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/orchestrate.md#L76)). `watch-pr` emits JSON by default.
- **Watcher output becomes the wake signal.** "Run `drive` and `background` under `/loop` in dynamic mode. Rearm the watcher after every push wave … Watcher output drives wakeups. Never add a second sleep loop." ([babysit.md L12](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/babysit.md#L12)). The blocking poll is in the Tool CLI, and the loop and wake belong to the Agent host.
- **Self-bootstrapping dependencies.** `orch` and `watch-pr` are `#!/usr/bin/env bun` scripts. They call `ensureDependenciesInstalled()`, which runs `bun install --frozen-lockfile` when a sha256 of `package.json`+`bun.lock` changes, then re-execs itself ([bootstrap.ts](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/bootstrap.ts#L17-L62)). The only runtime dependency is `commander` ([package.json](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/package.json)). As a result there is no separate CLI install step, but Bun must be on PATH. That requirement is inferred from the shebang and I found no doc that states it.
- **The CLIs are tested code.** `orch.test.ts`, `watch-pr/*.test.ts` and `check-plan.test.ts` exist, and `bun test` runs them ([package.json L5-L6](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/package.json#L5-L6)).
- **The design rationale is a principle skill.** "build-the-lever: Build the tool that does it or proves it (codemod, script, generator…) instead of working by hand", and "encode-lessons-in-structure: Encode the rule as a lint, metadata flag, runtime check, or script instead of more text" ([README principles table](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/README.md#L219-L253)). The playbooks cite these two principles when they call `check-plan.mjs` and `worktree-audit.sh`.

## Where state lives

- **Orchestration store.** This is a folder `orchestrate/<project-slug>/` "in the current agent's store (path in the system prompt)", where "every file has exactly one writer" ([orchestrate.md L21-L32](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/orchestrate.md#L21-L32)). `orch init` creates `units.tsv`, `ledger.tsv`, `inbox/`, `gates.md`, `preferences.md` (standing orders) and `frontier.json` ([store.ts L1648-L1655](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/orch/store.ts#L1648-L1655)). `orch status` regenerates `status.md` ([store.ts L1621](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/orch/store.ts#L1621)). The playbook also names `overview.md` and `decisions.tsv`, which agents write by hand or with `log.sh`. The data stays canonical plain TSV, JSON and Markdown, "readable without the CLI".
- **Concurrency.** `.orch.lock` holds the writer's pid. A stale lock whose pid is dead gets replaced, and `--force` steals a lock ([store.ts L370-L427](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/orch/store.ts#L370-L427); [orchestrate.md L102](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/orchestrate.md#L102)). Writes go through temp-file `atomicWrite` ([store.ts L340](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/orch/store.ts#L340)).
- **Verification ledger.** The ledger is keyed by PR plus head SHA. Its verdicts are `live-ui-verified | unit-test-verified | type-check-only | verifier-blocked | verifier-failed`, and "a new head SHA voids the row" ([orchestrate.md L90](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/orchestrate.md#L90); [store.ts L18-L26](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/scripts/orch/store.ts#L18-L26)).
- **Decision trail.** A TSV per run, "local by default; commit it when a reviewer needs the trail" ([show-me-your-work SKILL.md L3](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/show-me-your-work/SKILL.md#L3)).
- **Durable work state is in git and the forge.** After a Cursor restart, "reattach cloud work by PR and branch rather than agent id" ([orchestrate.md L102](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/orchestrate.md#L102)). Autopilot owners "assume the VM dies" and push early ([autopilot-full.md L12](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/autopilot-full.md#L12)).
- **Config.** `/setup-pstack` writes model-per-role choices to the always-applied rule `~/.cursor/rules/pstack-models.mdc` ([setup-pstack SKILL.md L8](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/setup-pstack/SKILL.md#L8)). In Claude Code the rule goes to `~/.claude/rules/pstack-models.md` ([claude-code.md](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/docs/harness/claude-code.md)).
- **Unverified.** I could not find where the "agent's store" is or what it is. The playbooks say only that the system prompt gives its path, which suggests a Cursor Agent host feature. Neither the Claude Code adapter doc nor any other pstack file maps it, so I don't know how `orch --store` is pointed in Claude Code.

## Supported Agent hosts

- **Cursor** is native. Install with `/add-plugin pstack`. It runs in the editor's agents window and in the Cursor CLI, and `/poteto-mode` can be kept on as a "custom mode" ([README L15-L18](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/README.md#L15-L18), [L104](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/README.md#L104)).
- **Claude Code** works through `/plugin marketplace add cursor/plugins` and `/plugin install pstack@cursor-plugins` ([README L22-L30](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/README.md#L22-L30)). The marketplace entry points at a **generated tree** `harness/pstack/claude-code` ([marketplace.json](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/.claude-plugin/marketplace.json)). [`scripts/generate-pstack-harness-trees.mjs`](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/scripts/generate-pstack-harness-trees.mjs#L1-L52) builds that tree from `pstack/` and scans skill text for Cursor-specific terms (`Task`, `environment: "cloud"`, `.cursor/rules`…). CI fails while the generated copy is stale. The scripts ship in the tree too ([harness tree](https://github.com/cursor/plugins/tree/d457567332aa6989e753ea289f30ea2bfbc80bc0/harness/pstack/claude-code/skills/poteto-mode/scripts)).
- **The adapter is prose, not code.** [`docs/harness/claude-code.md`](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/docs/harness/claude-code.md) is read once per session. It maps `Task`→`Agent` and `environment: "cloud"`→`isolation: "worktree"`, maps non-Claude models to "omit", and handles Cursor-only features (Automations, Bugbot, cloud agents) as "Skipped in Claude Code: <step>". pstack's own word for an Agent host is "harness", which is the reverse of our glossary.
- **Other hosts.** Codex, Pi, OpenCode, T3 and others are covered only by community ports such as [backnotprop/pstack](https://github.com/backnotprop/pstack), [michael-denyer/pstack-claude](https://github.com/michael-denyer/pstack-claude), [ScriptedAlchemy/pstack-codex](https://github.com/ScriptedAlchemy/pstack-codex) and [creedants/pstack-t3](https://github.com/creedants/pstack-t3). None of them is upstream, and I did not read any.

## Distribution

pstack is a plugin folder in the `cursor/plugins` monorepo, with Cursor and agent-plugins manifests ([plugin.json](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/plugin.json)) and Claude Code manifests in the generated tree. The CLIs travel inside the skill folder and install their own npm dependencies on first run. There is no npm, brew or binary release of the CLIs. The Benny automation pack is Cursor-only and gets copied into a target repo ([README L279-L283](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/README.md#L279-L283)).

## Mapping onto haai's three pains

| Pain | What pstack does | Takeaway for haai |
|---|---|---|
| **Deterministic flow steps** | Partial. Deterministic checks are Tool CLIs that a playbook step calls: a plan linter, a PR watcher with a terminal verdict, a worktree auditor and a log appender. The flow itself is still prose: `poteto-mode` copies playbook steps "verbatim" into a todo list ([README L96-L100](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/README.md#L96-L100)), and nothing enforces step order. | Their pattern is "encode the lesson as a script, call it from the step" (build-the-lever and encode-lessons-in-structure). There is no step-runner, so a haai CLI that owns step sequencing would go beyond pstack. |
| **AFK orchestration** | Done inside the Agent host. Cursor `/loop` provides wakes ([autonomous-run.md L6](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/autonomous-run.md#L6)), cloud agents act as workers and owners, a Cursor Project acts as the persistent coordinator thread ([07-overnight.md L96](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/docs/guide/07-overnight.md#L96)), and `/loop 1h` audits stuck agents ([autopilot-full.md L22](https://github.com/cursor/plugins/blob/d457567332aa6989e753ea289f30ea2bfbc80bc0/pstack/skills/poteto-mode/playbooks/autopilot-full.md#L22)). In Claude Code these map to background subagents and worktrees, and cloud and Automations steps are skipped. | pstack leans on host features. haai's Orchestrator CLI fills the gap pstack leaves open: driving headless sessions from outside, which keeps working without Cursor's cloud and loop. |
| **Observability / state** | Strong. Plain-file, single-writer store with a pid lock, a verification ledger keyed by PR+SHA, an inbox of completion pointers, parked human gates with defaults, a derived `status.md`, and a TSV decision trail. Compact three-line status output for the agent and `--json` for detail. | The design is directly reusable for haai: TSV/JSON/MD that stays readable without the CLI, one writer per file, a ledger keyed by head SHA, and derived status. The main open question is where the store lives when no host provides an "agent store" path. |

## Open questions surfaced

- What the Cursor "agent's store" is, and how pstack's Claude Code users point `orch --store` / `ORCH_STORE`. Neither is documented upstream.
- Whether `control-cli` in `cursor-team-kit` is a Tool CLI (for driving CLIs and TUIs for live verification). It was not read here.
- How the community ports (for example `creedants/pstack-t3`'s "brigade" coordinator and `ScriptedAlchemy/pstack-codex`) replace `/loop` and cloud agents, and whether any of them adds a real Orchestrator CLI.
